# DotNetro / Irie status report — 2026-10-07

Scope: state of the project and recommendations only. No plan of work.
Basis: a read-through of the repo layout, the pass pipelines, the RA files (skimmed,
not audited line by line), the notes and docs, the test suite (251 tests, all
passing), a run of the llvm-mos scoreboard under each allocator, and the current
llvm-mos `main` (`0f031168a7cc`, 2026-10-05) plus open PR #611 for its register
allocation direction.

Stated goal: **real C# programs running on a BBC Micro.** Best-in-class 6502 code is
a desirable follow-up, not the primary goal. Instruction count is a weak proxy for
quality and is used below only to compare our allocators with each other.

---

## 1. Summary

1. **The binding constraint on the stated goal is language/IR coverage, not code
   quality.** The IL→MIR translator implements 50 of 218 IL opcodes. Irie's generic
   MIR cannot express multiply, divide, shifts, bitwise ops, i64, or pointer/array
   memory access (loads and stores are only selected through `mem.symbol`
   addresses). Most non-trivial C# will not compile today.
2. **The code that runs on the emulator is not the code the lit goldens pin.** `dnrc`
   and `iriec` build different pass pipelines, and only `dnrc` output is ever
   executed. Several passes have never run against an execution check.
3. **Regalloc is in a bad structural state, and the reference is moving.** There are
   two allocator engines behind one wrapper, plus an incomplete SSA allocator and a
   coalescer pass, selected by environment variables (~5K lines). llvm-mos itself is
   mid-way through replacing its greedy-based allocation with an SSA pipeline that is
   mostly stubs. There is no finished design to port, which makes this the most open
   — and most interesting — part of the project, but also the worst place to invest
   before coverage exists.
4. **The measurement is not yet able to judge allocators.** The 24 blocked corpus
   cases are the high-pressure ones; 4 of the 23 converted cases duplicate others; the
   corpus is C-shaped (8/16-bit) while C# is 32-bit- and pointer-heavy.
5. **Docs and comments are stale enough to mislead agents** (CLAUDE.md describes the
   deleted string-based compiler; ~20 source comments point at deleted plans).

Recommended order (details in §8): fix CLAUDE.md and delete dead code → unify the
pipeline and execute `.irie` tests → add a post-RA verifier → widen coverage → only
then return to register allocation, against a corpus that includes C#-shaped code.

## 2. Pipeline and architecture

Shape (working well): IL → `IlToMirTranslator` (DotNetro.Compiler, ~2.9K lines) →
one unified MIR through ~25 passes → MachineCode → `MOS6502BinaryEncoder` → `.ssd`.
The old IL→asm string compiler (`DotNetCompiler.cs`, `M6502CodeGenerator.cs`, the
Sixty502 assembler path) is gone; the Irie path is the only path. The pass structure
mirrors llvm-mos closely.

Size: Irie ≈ 21K lines, Irie.Tests ≈ 3.6K, DotNetro.Compiler ≈ 2.9K, runtime
(`DotNetro/Runtime`) is two small C# files plus a 905-line hand-written
`runtime.irie`.

### 2.1 Duplicated, drifted pass pipelines
`src/Irie.Tools.Compiler/Program.cs` and `CompilerDriver.Compile`
(`src/DotNetro.Compiler/CompilerDriver.cs`) each list the passes by hand. They differ:

| Pass | `iriec` | `dnrc` (`CompilerDriver`) |
|---|---|---|
| `OperandLegalizationPass` | yes | **no** (self-described no-op today) |
| `RematerializableSinkPass` | yes | **no** |
| `RegisterCoalescerPass` (gated) | env var | no |
| `CopyPropagationPass` | yes | **no** |
| allocator selection | env vars | colourer only |

This cuts both ways:
- The 116 `iriec` lit tests pin output the real compiler does not produce.
- More importantly, **the only tests that execute code** — the 21 `.cs` programs run
  on the Aemula emulator — go through `dnrc`. The `.irie` tests are text goldens and
  never execute. So `CopyPropagationPass` and `RematerializableSinkPass` have never
  been checked for correctness by execution.

The fix is one `PipelineBuilder` (or `Target.BuildPipeline(options)`) used by both
tools. Expect it to surface bugs in the passes `dnrc` has been skipping; it is not a
purely mechanical change.

### 2.2 Verification gaps
- `.irie` tests check text only. Several corpus and codegen cases (fibonacci,
  select, if-else, many-calls, the i32 adds) could additionally be called on the
  emulator with a handful of inputs and their results checked. That gives every
  codegen change — RA, peepholes, frame lowering — an execution oracle, not just a
  diff.
- The only verifier is `GenericMirVerifierPass`, at the *start* of the pipeline.
  There is no post-RA verifier (no vregs except scavenger temps, no two
  simultaneously-live values in one physreg, operand-class and tied-operand
  constraints satisfied, flags not clobbered while live). This is cheap and
  independent of which allocator is in use.

### 2.3 Environment-variable switches in production tools
`IRIE_SSA_RA`, `IRIE_COALESCE`, `IRIE_GREEDY` (and `IRIE_RA_TRACE`) are read in
`Program.cs`/`RaTrace.cs`. They began as bring-up scaffolding and are how the
alternative allocators came to coexist. They should go, along with the alternatives
(§8).

### 2.4 "Funnel" legacy
The selector (`MOS6502InstructionSelector`, 1.6K lines) and RA still carry the
vocabulary and some code of the old "out-funnel" workaround (forced-`$a` results
copied into a flexible vreg): `InsertRelocationCopiesForConstrainedDefs` in the RA
pass, funnel-shaped pattern matching for the abs-load fold, two remaining "funnel out
of `$a`" sites in the selector, and `OperandLegalizationPass`, whose own header calls
it a verified no-op "until those funnels" are removed. These exist because constraint
handling lives inside the allocator; they would be reshaped by moving constraint
isolation ahead of RA (§7).

### 2.5 Smaller items
- `ReturnMergePass` + `TailDuplicationPass` (merge return blocks, then split trivial
  ones back after block placement) look redundant but deliberately mirror LLVM's
  SimplifyCFG-merge / TailDuplicate division of labour. Leave as is.
- `HoistCommonCodePass`, `ArithSimplifyPass`, `RematerializableSinkPass`,
  `MOS6502IncrementStrengthReductionPass`: useful, each with its own ad-hoc
  profitability check — fine for now.
- `RegisterScavengingPass` runs last and drives final lowering of copy-scratch vregs
  minted by pseudo expansion. This is llvm-mos order but means "no vregs left after
  RA" is not true; a post-RA verifier must allow for it.
- `lib/Sixty502` is referenced by no project and can be deleted. `lib/Aemula` is
  used by the emulator and compiler test projects.

## 3. Front end and coverage (the main gap)

`doc/dotnetro/il-support.md` (generated): 218 opcodes, 50 implemented, 31 with a
lit test. Notably absent: `and`/`or`/`xor`/`not`/`neg`, `mul`/`div`/`rem`,
`shl`/`shr`, `ceq`/`cgt`, the compare-and-branch family (`beq`, `bge`, `blt`, …),
`conv.i1/i2/i4/i8` and `conv.u*`, `switch`, arrays (`newarr`, `ldelem`,
`stelem`, `ldlen`), `ldind`/`stind` beyond `stind.i`/`ldind.u1`, `box`, `castclass`,
`isinst`, i64.

On the Irie side the corpus README's blocked-case table is the same list from the
other end: no `arith` multiply/divide/shift/bitwise, no i64, no `zext`/`sext` to i32,
loads and stores only through symbols (`SelectMemLoadByteAt` handles only a
`mem.symbol` address; frame-slot and heap pointers are not yet supported), no
multiway branch, no aggregate/sret ABI.

Compiler tests (`DotNetro.Compiler.Tests/Lit`) are 21 programs: classes, structs,
virtual calls, static fields, a for-loop, Console I/O. The OO core (vtables,
`newobj`, `ManagedHeap`, static ctors, string literals) is already present, which is
a good base. The gaps are mostly *arithmetic and memory-access breadth*, which need
work in three layers at once (translator → generic MIR → legalizer/isel).

Because each missing operation is blocked at several layers, the corpus README's
blocker table is a ready-made, correctly ordered punch list, and the corpus cases
double as acceptance tests. For C#, the first priorities are **32-bit arithmetic
breadth and loads/stores through arbitrary pointers**: `int` is 32-bit, and arrays,
strings and object fields all go through pointers.

## 4. Measurement

### 4.1 Corpus
- 23 converted cases, 24 blocked. The blocked ones are the high-pressure ones
  (`pressure-high`, `pressure-i64`, `nested-loop`, `crc8`, …), so allocators are
  being compared on the easy half.
- The four `coalescing/` cases are, per the README, the same MIR shapes as `add-i16`,
  `identity-i8`, `select` and `sub-i16`. They double-count four existing cases and
  do not exercise coalescing beyond them.
- Irie's total (568 instructions) is 16% *below* llvm-mos's (676). That should be
  read as a sign the comparison has a bias (case selection, ABI or prologue
  differences, what each side counts), not as Irie being better. It needs explaining
  before totals are used to choose between designs.
- The corpus is translated from llvm-mos C, so it is mostly 8/16-bit. Quality on real
  C# will be dominated by i32 arithmetic, runtime helper calls (multiply/divide), and
  pointer-based field and element access. A small C#-derived benchmark set alongside
  the C corpus would keep tuning aimed at the actual workload.
- The reference itself will shift: when llvm-mos moves to its new allocator (§6), its
  output — and therefore the scoreboard baseline — will change.

### 4.2 Metrics
- **Code bytes** are available today from `--emit=bin` with no emulator work, and on
  a BBC Micro memory is usually the tighter constraint. Add bytes alongside
  instruction count now.
- **Cycles** would need instrumentation in the emulator harness; Aemula is consumed
  as a prebuilt DLL and whether it exposes a cycle counter has not been checked.
  Lower priority than bytes.

## 5. Register allocation: current state

### 5.1 What is in the tree

| Component | Lines | Status |
|---|---|---|
| `RegisterAllocatorPass` (wrapper, spill loop, rematerialize, store/reload, `TrySplitToRegister`, relocation-copy insertion) | 743 | serves both engines |
| `GraphColouringAllocator` (iterated register coalescing) | 1363 | **default** |
| `GreedyRegisterAllocator` | 871 | opt-in `IRIE_GREEDY=1` |
| `SplitEditor` (SplitKit analogue) | 1064 | greedy only |
| `RegisterCoalescerPass` | 171 | opt-in `IRIE_COALESCE=1`; crashes/errs with greedy |
| `SsaRegisterAllocatorPass` | 591 | opt-in `IRIE_SSA_RA=1`; no phi support |
| `OperandLegalizationPass`, `RegisterAllocationSupport`, `LiveIntervals*`, `RaTrace` | ~1.3K | shared/support |

### 5.2 Measured (instruction counts, 23 converted corpus cases)

| Allocator | Total | Notes |
|---|---:|---|
| llvm-mos (reference) | 676 | see §4.1 caveat |
| **Graph colourer (default)** | **568** | no errors |
| Greedy | 591 | no errors; worse on stack-args (+10), global-rw (+3), live-across-call (+2), many-calls (+2), fibonacci (+1) |
| Greedy + coalescer | — | 14 of 23 cases error |
| SSA | — | 7 of 23 cases error; 365 vs 434 on the 16 that run |

Read these as: *the colourer is a bit ahead of greedy on this corpus, and neither the
SSA allocator nor the coalescer is usable yet.* With four cases duplicated and the
high-pressure half missing, the corpus cannot separate the designs further.

`notes/greedy-default-plan.md` argues for making greedy the sole allocator, chiefly
because llvm-mos used RegAllocGreedy and so greedy design questions had a canonical
reference answer. That premise no longer holds (§6), and its numbers (17 cases) are
out of date.

### 5.3 Why it feels like "every new thing rewrites a chunk"
From the code and history (~40 RA-related commits since May 2026; colourer → greedy →
SplitKit port → SSA → coalescer), the recurring pattern is that the allocator is
asked to do four different jobs at once, and each new requirement lands on a
different one:

1. **Constraint satisfaction** — tied operands (`adc`: result and one input in `$a`),
   single-register classes (`ac`, `xc`, `yc`), flag registers, calling-convention
   physregs, clobbers across calls.
2. **Fit** — can the values be held at all.
3. **Placement / cost** — on this target almost everything fits because zero page
   is a big pool of pseudo-registers; the real question is *which few values get
   the 3 scarce real registers*, since GPR↔zp is 1 byte/2 cycles vs 2 bytes/3+ cycles
   per access and many operations only exist on `$a`.
4. **Real spilling** — to memory; rare here (soft stack / frame slots).

Each allocator tried so far bakes jobs 1–3 into one mechanism: the colourer encodes
placement as class intersection + colour order; greedy as hints + eviction +
splitting; SSA as relocation-product ordering. Constraints in particular are handled
by inserting compensating copies (`InsertRelocationCopiesForConstrainedDefs`,
TwoAddress copies, `TrySplitToRegister`, funnels) whose shape each allocator then has
to cooperate with. That coupling is the root of the churn. It is not inherent to
regalloc; it is inherent to *letting constraint handling live inside the allocator*.

## 6. Where llvm-mos is going

llvm-mos is replacing its conventional (greedy-based) allocation for MOS with an
experimental SSA pipeline, behind `-mos-experimental-regalloc` (off by default):

```
… → MOSConventionalSSA → MOSImagRegAlloc → MOSRegAlloc → StackSlotColoring → …
```

- **`MOSConventionalSSA`** (implemented, #606, 2026-10-05): isolates every PHI's
  inputs and result with parallel copies (one outgoing PCOPY per predecessor, which
  also handles critical edges without changing the CFG), and normalizes tied operands
  so each tied input dies at its instruction and a tied def is a continuation of the
  use's live range. This is constraint isolation as a separate pre-RA pass.
- **`MOSImagRegAlloc`** (stub): assign imaginary (zero-page) registers and insert
  spills/reloads, staying in SSA. Its header describes whole-function graph colouring.
- **`MOSRegAlloc`** (stub): choose hardware placements (A/X/Y vs imaginary) and emit
  transfers using the treewidth dynamic programming approach from SDCC (Krause,
  *Optimal Register Allocation in Polynomial Time*, CC 2013) — a cost search over
  per-instruction operand placements and transfer costs between neighbouring
  instructions. It also eliminates PHIs and lowers parallel copies. The header says
  this "has only been prototyped, but not yet upstreamed".
- **Open PR #611** implements straight-line (single-block) imaginary-register
  spilling as a *treescan* spiller, and splits the old allocator into a treescan
  spiller, a later whole-function PHI spiller, and a separate assignment pass —
  "a shift from a pure graph coloring approach back to a treescan allocator".

Consequences for Irie:
- **Greedy has lost its "follow the reference" rationale.** The reference is leaving it.
- **The new structure matches the separation argued for in §5.3**: constraints
  isolated first; fit/spill decided in SSA; hardware placement as a global cost
  problem, separate from fit.
- **There is no finished design to port.** The two allocation passes are stubs, the
  spill approach changed within weeks, and the placement algorithm is unpublished
  apart from the SDCC literature. 6502 register allocation is still an open problem,
  so Irie can do original work here rather than catch-up porting — but it should not
  bet on details that llvm-mos itself is still revising.

## 7. Regalloc direction (for discussion, not a decision)

Principles, consistent with where llvm-mos is heading:

**P1. Make constraints explicit in the IR before allocation, and make them local.**
A conventional-SSA pass in the style of `MOSConventionalSSA`: isolate block
parameters with parallel copies and normalize tied operands so a tied def continues
its use's range. Pinned-register operands get short instruction-local ranges joined by
ordinary copies. Constraint handling then stops being an allocator feature: a new
opcode or ABI rule changes this pass, not the allocator. This is the one piece with an
implemented, tested reference (296 lines plus `.mir` tests), and it replaces
`InsertRelocationCopiesForConstrainedDefs`, the funnel remnants and much of
`TwoAddressInstructionPass`'s role.

**P2. Separate "does it fit" from "who gets which register".**
A pressure/spill phase that guarantees assignment cannot fail (on 6502 almost always
trivial, given zero page), then an assignment phase. Each can be tested and replaced
independently; a new spill strategy (e.g. soft-stack slots) touches only the first.
Whether the spill phase colours a graph or scans a dominator tree is exactly what
llvm-mos is still deciding; for Irie, where spilling is rare, the simplest correct
option is enough.

**P3. Treat hardware-register placement as an explicit cost problem.**
Since fit is rarely the issue, quality is decided by which values get `$a`/`$x`/`$y`
over which ranges. Make that a standalone, replaceable component with a per-range
benefit model (bytes and cycles saved, loop-depth weighting, copies removed). The
SDCC treewidth DP is the most principled known option and the one llvm-mos intends to
use; a simpler heuristic version first is reasonable. This is where greedy's
machinery (spill weights, hints, region splitting) was trying to live.

**P4. Make the allocator's output verifiable independent of its inner workings.**
The post-RA verifier and the executed `.irie` tests (§2.2) catch bugs in any
allocator cheaply and let alternatives be A/B tested with confidence. These come
first, before any allocator work.

Sketch: `… isel → conventional SSA (P1) → pressure/spill (P2) → placement +
assignment (P3) → phi/parallel-copy lowering → copy elimination → …`. Whether this
beats the current colourer is an empirical question. The claim is that it localizes
future change, which is the property that has been missing.

Risks: isolation copies must reliably vanish; the existing SSA allocator's partial
results (365 vs 434 on 16 cases) are encouraging but unrepresentative since it
errors on 7; and tracking a moving reference costs time, so revisit llvm-mos's state
when this work starts rather than now.

## 8. Recommendations

Ordered by value to the stated goal.

1. **Fix CLAUDE.md and delete dead code (cheap, do first).** CLAUDE.md still describes
   `DotNetCompiler.cs`, `M6502CodeGenerator` and the Sixty502 path, and says Irie is
   "not yet wired into the main compiler"; agents treat it as authoritative. Repoint
   or remove the ~20 source and test comments that cite 8 deleted plans
   (`register-allocator-redesign-plan`, `generic-relocation-pass-plan`,
   `mir-to-machinecode-plan`, `unified-ir-plan`, …). Delete `lib/Sixty502` and
   `notes/greedy-default-plan.md`.
2. **Delete the alternative allocators and their switches.** Remove
   `GreedyRegisterAllocator`, `SplitEditor`, `RegisterCoalescerPass`,
   `SsaRegisterAllocatorPass` and the `IRIE_*` allocator env vars in one change; keep
   the colourer as the sole allocator. Greedy's reference rationale is gone (§6), and
   the SSA attempt is better restarted from P1 than resumed. Git history preserves all
   of it for salvage.
3. **Unify the pass pipeline** (§2.1) so `dnrc` and `iriec` run the same passes.
   Budget for the bugs this exposes in passes `dnrc` has been skipping.
4. **Add execution and verification** (§2.2): run selected `.irie` cases on the
   emulator with checked results, and add a post-RA verifier. Both pay off for every
   later codegen change, whatever allocator is in use.
5. **Widen coverage, driven by the blocked corpus list** (§3). Priority for C#:
   i32 arithmetic breadth (bitwise ops, shifts, `ceq`/`cgt`/compare-branch family,
   `conv.*`, zext/sext), arbitrary-pointer `mem.load`/`mem.store` (unlocks arrays,
   strings, fields through refs), multiply/divide via runtime calls, then `switch`,
   then i64 and aggregate ABI. Each new case adds a high-pressure allocator test.
6. **Improve the measurement** (§4): add code bytes now; remove or rewrite the four
   duplicate `coalescing/` cases; explain the 568-vs-676 gap; add a small C#-derived
   benchmark set; report the scoreboard from one command.
7. **Then return to register allocation** (§7) as a bounded effort with explicit exit
   criteria (all converted cases compile and execute correctly; totals on the full
   corpus within a stated tolerance of the colourer; no case-specific code). Start
   with P1 (conventional-SSA constraint isolation) — it has a working reference and
   pays off even under the colourer. Re-check llvm-mos's experimental pipeline at that
   point before committing to the spill and placement designs.
8. **Later / lower priority**: the runtime story (heap, strings, `Console`) as a
   separate review once coverage widens; best-in-class code-quality work (strength
   reduction, closed-form loops such as `loop-counter`) follows the goal.

## 9. Open questions
- Does Aemula expose cycle counts cheaply enough to use as a metric? (Not checked.)
- What explains Irie's 16% lower instruction total versus llvm-mos — corpus
  selection, ABI/prologue differences, or counting?
- When the placement problem is tackled, is SDCC's treewidth DP practical at Irie's
  scale, or does a simpler range-benefit heuristic capture most of the value first?
- Is anything in `GreedyRegisterAllocator`/`SplitEditor` (spill weights, value-numbered
  live intervals) worth keeping before deletion, e.g. moving value numbers into the
  shared `LiveIntervals`? (Needs a read beyond the skim done here.)
