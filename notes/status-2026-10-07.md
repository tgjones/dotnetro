# DotNetro / Irie status report — 2026-10-07

Scope: state of the project and recommendations only. No plan of work.
Basis: a read-through of the repo layout, the pass pipelines, the RA files (skimmed,
not audited line by line), the notes and docs, plus a fresh `dotnet test --solution src`
(251 tests, all pass, ~20 s) and a fresh run of the llvm-mos scoreboard under each
allocator. llvm-mos PR #611 was read only for its description.

Stated goal: **real C# programs running on a BBC Micro.** Best-in-class 6502 code is
a desirable follow-up, not the primary goal. Instruction count is a weak proxy for
quality and is used below only to compare our allocators with each other.

---

## 1. Summary

1. **The binding constraint on the stated goal is language/IR coverage, not code
   quality.** The IL→MIR translator implements 50 of 218 IL opcodes. Irie's generic
   MIR cannot express multiply, divide, shifts, bitwise ops, i64, or pointer/array
   memory access (`mem.load`/`mem.store` accept only `mem.symbol` addresses). Most
   non-trivial C# will not compile today.
2. **Regalloc is in a bad structural state.** There are four allocation paths in
   the tree (~5K lines), one of them the default, and the pass pipeline that
   `dnrc` actually runs has drifted from the one the tests exercise. The allocator
   *design* is the concern, more than any single path's quality.
3. **The corpus cannot judge allocators yet.** The 24 corpus cases that are
   blocked are the high-pressure ones (`pressure-high`, `pressure-i64`,
   `nested-loop`, `crc8`, …). Allocators are being compared on the easy half.
4. **Several docs are stale** (CLAUDE.md, `notes/greedy-default-plan.md`, a comment
   in `RegisterAllocatorPass.cs` pointing at a deleted plan).

Recommended order (details in §6): fix the pipeline duplication → widen coverage
(this also unblocks the corpus) → define better metrics → *then* do the fresh
regalloc design against the full corpus, and delete the rest.

## 2. Pipeline and architecture

Shape (working well): IL → `IlToMirTranslator` (DotNetro.Compiler, ~2.9K lines) →
one unified MIR through ~25 passes → MachineCode → `MOS6502BinaryEncoder` → `.ssd`.
The old IL→asm string compiler (`DotNetCompiler.cs`, `M6502CodeGenerator.cs`) is
gone; the Irie path is the only path. Lit tests (`.irie`, `.s`, `.cs`) plus the
Aemula emulator end-to-end tests give good regression protection. The pass
structure mirrors llvm-mos closely and is documented well in CLAUDE.md.

Size: Irie ≈ 21K lines, Irie.Tests ≈ 3.6K, DotNetro.Compiler ≈ 2.9K, runtime
(`DotNetro/Runtime`) is two small C# files plus a 905-line hand-written
`runtime.irie`.

### 2.1 Duplicated, drifted pass pipelines
`src/Irie.Tools.Compiler/Program.cs` and `CompilerDriver.Compile`
(`src/DotNetro.Compiler/CompilerDriver.cs`) each list the passes by hand. They differ:

| Pass | `iriec` | `dnrc` (`CompilerDriver`) |
|---|---|---|
| `OperandLegalizationPass` | yes | **no** |
| `RematerializableSinkPass` | yes | **no** |
| `RegisterCoalescerPass` (gated) | env var | no |
| `CopyPropagationPass` | yes | **no** |
| allocator selection | env vars | colourer only |

So the lit tests that pin `iriec` output are not testing what the real compiler
produces for C# programs. This is the cheapest, highest-value structural fix:
one `PipelineBuilder` (or `Target.BuildPipeline(options)`) used by both.

### 2.2 Environment-variable switches in production tools
`IRIE_SSA_RA`, `IRIE_COALESCE`, `IRIE_GREEDY` (and `IRIE_RA_TRACE`) are read in
`Program.cs`/`RaTrace.cs`. They are fine as bring-up scaffolding but they are how
four allocators ended up coexisting. They should become explicit options while any
alternatives remain, and disappear with the alternatives.

### 2.3 Passes that undo each other
`ReturnMergePass` merges return blocks (SimplifyCFG analogue) and
`TailDuplicationPass` splits trivial ones back (placed *after* block placement because
placement has no integrated tail-dup). It works and is golden-tested, but it is
two passes with a cost-model-free merge followed by a cost-model-aware split; a
single decision would be simpler. Low priority.

### 2.4 "Funnel" legacy
The selector (`MOS6502InstructionSelector`, 1.6K lines) and RA still carry the
vocabulary and some code of the old "out-funnel" workaround (forced-`$a` results
copied into a flexible vreg): `InsertRelocationCopiesForConstrainedDefs` in the RA
pass, funnel-shaped pattern matching for the abs-load fold, and
`OperandLegalizationPass`, whose own header calls it a verified no-op "until those
funnels" are removed. These exist because of how the colourer handles constraints
and would be reshaped by any allocator redesign (§5).

### 2.5 Smaller items
- `HoistCommonCodePass`, `ArithSimplifyPass`, `RematerializableSinkPass`,
  `MOS6502IncrementStrengthReductionPass`: useful, but each is a bespoke pass
  without a shared framework for "is this profitable" — fine for now.
- `RegisterScavengingPass` runs last and drives final lowering of copy-scratch
  vregs minted by pseudo expansion. This is llvm-mos order but means "no vregs left
  after RA" is not actually true; worth remembering when redesigning RA.
- Uncommitted working tree: new `coalescing/` corpus tests, regenerated
  comparison doc, README and `select.irie` edits.

## 3. Front end and coverage (the main gap)

`doc/dotnetro/il-support.md` (generated): 218 opcodes, 50 implemented, 31 with a
lit test. Notably absent: `and`/`or`/`xor`/`not`/`neg`, `mul`/`div`/`rem`,
`shl`/`shr`, `ceq`/`cgt`, the compare-and-branch family (`beq`, `bge`, `blt`, …),
`conv.i1/i2/i4/i8` and `conv.u*`, `switch`, arrays (`newarr`, `ldelem`,
`stelem`, `ldlen`), `ldind`/`stind` beyond `stind.i`/`ldind.u1`, `box`, `castclass`,
`isinst`, i64.

On the Irie side the README's blocked-case table is the same list from the other
end: no `arith` multiply/divide/shift/bitwise, no i64, no `zext`/`sext` to i32, loads
and stores only through symbols, no multiway branch, no aggregate/sret ABI.

Compiler tests (`DotNetro.Compiler.Tests/Lit`) are 21 programs: classes, structs,
virtual calls, static fields, a for-loop, Console I/O. The OO core (vtables,
`newobj`, `ManagedHeap`, static ctors, string literals) is already present, which is
a good base; the gaps are mostly *arithmetic and memory-access breadth*, which
need work in three layers at once (translator → generic MIR → legalizer/isel).

Observation: because each missing operation is blocked at several layers, the
corpus README's blocker table is a ready-made, correctly-ordered punch list. The
corpus cases double as acceptance tests.

## 4. Register allocation: current state

### 4.1 What is in the tree

| Component | Lines | Status |
|---|---|---|
| `RegisterAllocatorPass` (wrapper, spill loop, rematerialize, store/reload, `TrySplitToRegister`, relocation-copy insertion) | 743 | serves both engines |
| `GraphColouringAllocator` (iterated register coalescing) | 1363 | **default** |
| `GreedyRegisterAllocator` | 871 | opt-in `IRIE_GREEDY=1` |
| `SplitEditor` (SplitKit analogue) | 1064 | greedy only |
| `RegisterCoalescerPass` | 171 | opt-in `IRIE_COALESCE=1`; crashes/errs with greedy |
| `SsaRegisterAllocatorPass` | 591 | opt-in `IRIE_SSA_RA=1`; no phi support |
| `OperandLegalizationPass`, `RegisterAllocationSupport`, `LiveIntervals*`, `RaTrace` | ~1.3K | shared/support |

### 4.2 Measured today (instruction counts, 23 converted corpus cases)

| Allocator | Total | Notes |
|---|---:|---|
| llvm-mos (reference) | 676 | |
| **Graph colourer (default)** | **568** | no errors |
| Greedy | 591 | no errors; worse on stack-args (+10), global-rw (+3), live-across-call (+2), many-calls (+2), fibonacci (+1) |
| Greedy + coalescer | — | 14 of 23 cases error |
| SSA | — | 7 of 23 cases error; 365 vs 434 on the 16 that run |

Because instruction count is a weak proxy, read these as: *the colourer is a bit
ahead of greedy on this corpus, and neither SSA nor coalescing is usable yet*.
Nothing here says greedy is a bad idea; it says it is incomplete.

`notes/greedy-default-plan.md` (the last written plan) quotes 17 converted cases and
325 vs 315 and is out of date; its central conclusion — greedy cannot beat the
colourer without region splitting (EdgeBundles + SpillPlacement) and
rematerialization as one coherent piece — still looks right, and is a large piece.

### 4.3 Why it feels like "every new thing rewrites a chunk"
From the code and history (~90 RA-related commits since mid-2026; colourer → greedy →
SplitKit port → SSA → coalescer), the recurring pattern is that the allocator is
asked to do four different jobs at once, and each new requirement lands on a
different one:

1. **Constraint satisfaction** — tied operands (`adc`: result and one input in `$a`),
   single-register classes (`ac`, `xc`, `yc`), flag registers, calling-convention
   physregs, clobbers across calls.
2. **Fit** — can the interference graph be coloured at all.
3. **Placement / cost** — on this target almost everything "fits" because zero page
   is a big pool of pseudo-registers; the real question is *which few values get
   the 3 scarce real registers*, since GPR↔zp is 1 byte/2 cycles vs 2 bytes/3+ cycles
   per access and many operations only exist on `$a`.
4. **Real spilling** — to memory; rare here (soft stack / frame slots).

Every allocator we tried bakes jobs 1–3 into one mechanism. The colourer encodes
placement as class intersection + colour order; greedy as hints + eviction + splitting;
SSA as relocation-product ordering. Constraints in particular are handled by
inserting compensating copies (`InsertRelocationCopiesForConstrainedDefs`,
TwoAddress copies, `TrySplitToRegister`, funnels) whose shape each allocator then has
to cooperate with. That coupling is the red flag the user noticed. It is not
inherent to regalloc in general; it is inherent to *letting constraint handling live
inside the allocator*.

## 5. Fresh thinking on a regalloc design (for discussion, not a decision)

Principles suggested by the evidence above:

**P1. Make constraints explicit in the IR *before* allocation, and make them local.**
Every constrained operand gets a short, instruction-local live range joined to the
rest of the program by an ordinary `pseudo.copy` (what `SsaRegisterAllocatorPass`
step 1 does, and what TwoAddress already does in part). After that, the allocator
sees only two kinds of vreg: *free* (any of the allocatable set) and *pinned to a
physreg for one instruction*. Constraint handling stops being an allocator feature,
so a new constraint (new opcode, new ABI rule) changes the IR-shaping pass, not the
allocator. Copies that turn out to be no-ops are removed by copy elimination.

**P2. Separate "does it fit" from "who gets which register".**
This is the structure of llvm-mos PR #611 and of Hack/Braun SSA allocation:
(a) a *pressure phase* that spills/rematerializes until max pressure ≤ k at every point
(on 6502: k = 3 real GPRs + the zp pool, so this phase is almost always trivial),
then (b) an *assignment phase* that cannot fail. Each phase can be tested and
replaced independently. Needing a new spill strategy (e.g. a soft-stack slot) should
touch only phase (a).

**P3. Treat 6502 placement as an explicit cost problem with its own small component.**
Since fit is rarely the issue, the quality-determining decision is "which values
get `$a`/`$x`/`$y` and for which ranges". That can be a standalone, replaceable
*placement policy* feeding hints (or hard preferences) to the assignment phase: a
per-vreg/per-range benefit estimate (bytes+cycles saved by being in a GPR; loop depth
weighting; how many copies it removes) and a simple, global selection under the
3-register capacity — knapsack-ish over intervals, not an eviction dance. This is
where greedy's accumulated machinery (spill weights, hints, region split) is trying to
live; making it a first-class, separately-testable piece avoids re-deriving it
inside whatever allocator we choose.

**P4. Stay in SSA through allocation if phis can be handled cleanly.**
Chordal-graph colouring on SSA is simple and provably succeeds at pressure ≤ k.
The SSA attempt stalled on phis (block parameters). The standard answer is to colour
phis/block parameters like any other def and lower the per-edge parallel copies
afterwards. `MOS6502ParallelCopyPass` and `PhiEliminationPass` already exist, so the
missing piece is probably smaller than the old attempt made it look. This needs a
spike to confirm, not an assumption. (Caveat to check: 6502 two-address instructions
and `$a`-pinned tied operands interact with SSA colouring; P1 is what makes them
manageable.)

**P5. Make the allocator's output verifiable independent of its inner workings.**
A post-RA verifier (no vregs, no two live values in one physreg, constraints
satisfied) plus a differential run of the emulator tests across allocator variants
would catch bugs in any future allocator cheaply and let alternatives be A/B tested
with confidence. The emulator can also report **cycles and bytes**, both better
metrics than instruction count.

Sketch of a pipeline under these principles:
`… isel → constraint-isolation (P1) → pressure/spill+remat (P2a) → placement policy
(P3) → SSA assignment with hints (P2b/P4) → phi/parallel-copy lowering → copy
elimination → …`. Whether this beats the current colourer is an empirical question;
the claim is only that it should localise future change, which is the property the
user asked for.

Risks: the isolation-copy approach produces many copies that must reliably vanish;
the SSA attempt's partial results (365 vs 434 on 16 cases) are encouraging but
unrepresentative, since it errored on 7. Greedy's accumulated work (spill weights,
split logic, SplitKit) is a real asset to salvage selectively, not wholesale.

## 6. Recommendations

Ordered by value to the stated goal.

1. **Unify the pass pipeline** (§2.1). Small, mechanical, removes a class of "tests
   pass but real compile differs" risk. Do it before further codegen tuning so
   improvements measured in lit tests reach `dnrc`.
2. **Widen coverage, driven by the blocked corpus list** (§3). Rough priority:
   bitwise ops and shifts, `ceq`/`cgt`/compare-branch family and `conv.*`,
   zext/sext, arbitrary-pointer `mem.load`/`mem.store` (unlocks arrays, strings,
   struct fields through refs), multiply/divide (likely via runtime calls), then
   `switch`, then i64 and aggregate ABI. Each new case immediately adds a high-pressure
   test for the allocator work.
3. **Improve the measurement** before the allocator redesign: (a) add cycles and
   code bytes (from the emulator or a static cost table) alongside instruction
   count; (b) keep the corpus scoreboard but report it per allocator variant from one
   command; (c) add the emulator-based differential correctness run across
   allocator variants.
4. **Then do the fresh regalloc design** (§5) as a bounded spike with a time box and
   explicit exit criteria (all converted corpus cases compile and are correct;
   total on the *full* corpus within some tolerance of the colourer; no
   case-specific code). Until then, **keep the colourer as the default** and freeze
   greedy/SSA/coalescer, not extend them.
5. **Delete what loses.** Whichever design wins, remove the others in one change,
   including the env switches, the funnel remnants, and the dead split kinds. Four
   coexisting allocators are a maintenance and comprehension cost out of proportion
   to their value; git history preserves them. If a clear decision is not reached
   soon, at minimum delete `SsaRegisterAllocatorPass` (abandoned, incomplete) and gate
   nothing else behind env vars.
6. **Refresh the docs**: CLAUDE.md (still describes `DotNetCompiler.cs`,
   `M6502CodeGenerator`, the Sixty502 assembler path; `lib/Sixty502` is still
   referenced only by the emulator test projects), `notes/greedy-default-plan.md`
   (stale numbers), and the dangling comment in `RegisterAllocatorPass.cs`.
7. **Later / lower priority**: unify ReturnMerge/TailDuplication into one
   cost-aware decision; the runtime story (heap, strings, `Console`) is a separate
   review once coverage widens; best-in-class code-quality work (strength reduction,
   region splitting, closed-form loops such as `loop-counter`) follows the goal.
