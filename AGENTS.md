# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, etc.) when working with code in this repository.

## What This Project Is

DotNetro is a .NET AOT compiler that compiles .NET assemblies (IL bytecode) to 6502 machine code, targeting retro computers like the BBC Micro. It reads ECMA-335 metadata, translates IL to Irie MIR (a compiler IR modelled on LLVM's GlobalISel / llvm-mos), runs the MIR through a pass pipeline (legalize → select → place values in registers → …), encodes the result to raw 6502 bytes, and packages them into a BBC Micro disk image (`.ssd`).

## Build & Test Commands

```bash
# Build and run all tests
dotnet test --solution src

# Run tests for a specific project
dotnet test --project src/DotNetro.Compiler.Tests
dotnet test --project src/Irie.Tests
dotnet test --project src/DotLit.Tests

# Filtering: TUnit uses --treenode-filter (NOT --filter, which silently runs zero tests).
# The path is /Assembly/Namespace/Class/Method — escape literal '.' in the displayed
# name as itself; the renderer shows '·' but you type '.'.

# Run all tests in a unit-test class
dotnet test --project src/Irie.Tests --treenode-filter "/*/*/RegisterAllocatorTests/*"

# Run a single unit-test method by name
dotnet test --project src/Irie.Tests --treenode-filter "/*/*/*/AAndXLiveAcrossCopy_PicksY"
```

**To run an individual lit test**, filter on its `Category`, which is the file name without
its extension (`--treenode-filter` cannot see the file in the test's display name, which is why
each test row carries it as a category; files with the same name in different folders both run):

```bash
dotnet test --project src/DotNetro.Compiler.Tests --treenode-filter "/*/*/*/*[Category=StructByValue]"
dotnet test --project src/Irie.Tests --treenode-filter "/*/*/*/*[Category=crc8]"
```

Both lit suites are fast (Irie.Tests ~3s, DotNetro.Compiler.Tests ~9s; the whole solution
~12s). They are fast because a `RUN` pipeline of our own tools (`@iriec`, `@dnrc`,
`@cs_compiler`, `@emulator`, …) runs **in the test process**, not as one process per tool
(see "In-process tools" below):

```bash
dotnet test --project src/Irie.Tests              # all Irie tests incl. every .irie/.s lit test
dotnet test --project src/DotNetro.Compiler.Tests # all compiler tests incl. every .cs lit test
```

CI runs `dotnet test --solution src` in both Debug and Release configurations.

## Code Documentation

Document types and members with `///` XML doc comments (`<summary>`, with longer explanation in `<remarks>`), not `//` blocks above declarations. Plain `//` is for comments inside method bodies, group/section labels, and lit-test directives (`RUN:`/`CHECK:`).

## Architecture

### Compilation Pipeline

```
.NET Assembly (.dll)
    → IlToMirTranslator  (DotNetro.Compiler: reads ECMA-335 metadata, walks IL, builds an Irie MirModule;
                          links in the hand-written runtime from Irie's runtime.irie)
    → Irie pass pipeline (AbiLowering → Legalizer → InstructionSelector → … → RegisterAllocator → … → PseudoExpansion)
    → MachineCodeEmitter → MOS6502BinaryEncoder  (MIR → MachineCode → raw 6502 bytes at the origin)
    → Target.PackageImage  (BBC Micro: single-file DFS .ssd)
```

`CompilerDriver.Compile` (`DotNetro.Compiler`) wires this together for `dnrc`; `Irie.Tools.Compiler` (`iriec`) handles MIR text input. **Both build their pass list from the single `PipelineBuilder.AddStandardPipeline` (`Irie/Passes/PipelineBuilder.cs`)**, so add or reorder passes there — lit goldens and emulator-executed programs exercise the same passes.

### Key Projects

- **DotNetro.Compiler** — IL front end; translates a .NET assembly into an Irie `MirModule`
  - `IlToMirTranslator.cs` — the IL→MIR translator (~1.8K lines). Queue-based discovery: `_methodsToVisit` is drained, vtable slot methods and static constructors re-seeded, repeated to a fixpoint. Builds vtables for every `newobj`'d type, string constants, and static-field globals. Not every IL opcode is implemented — see `doc/dotnetro/il-support.md` (generated by `DotNetro.Tools.ILSupport`). Unsupported opcodes fail the compile.
  - `CompilerDriver.cs` — `Compile(assemblyPath, entryPoint)` (file-based wrapper used by `dnrc`) and `Compile(CompileRequest)` (byte-based, no file system; takes an `IAssemblyResolver` and a `TargetRegistry` id; expected failures come back as `Diagnostics`): translate, run the pass pipeline, emit machine code, encode, package the image. `AssemblyResolver.cs` has `HostAssemblyResolver` / `InMemoryAssemblyResolver`; `TargetRegistry.cs` maps target ids to Irie targets and the assemblies they link against
  - `TypeSystem/TypeSystemContext.cs` — type resolution cache; types are lazily resolved (EnsureFields, EnsureBaseType pattern)
  - `EcmaAssembly/EcmaType/EcmaMethod/EcmaField` — wrappers over System.Reflection.Metadata. `[MethodImpl(InternalCall)]` methods (e.g. `PutChar`) have no IL body: the translator routes calls to the matching hand-written function in `runtime.irie`.

- **DotNetro.Compiler.Driver** — console app (`dnrc`); CLI flags `--assembly`, `--output`, `--emit`

- **DotNetro.CoreLib** / **DotNetro.CoreLib.BbcMicro** — DotNetro's own core library (assembly `DotNetro.CoreLib`, built `NoStdLib` so it defines `System.Object` etc. itself; never loaded by the .NET runtime, only read by the compiler). The sources live in `src/DotNetro.CoreLib/` (no project there; shared properties in `CoreLib.props`) and are compiled once per target by `DotNetro.CoreLib.<Target>`: every plain `*.cs` file plus that target's `*.<Target>.cs` files (e.g. `Console.cs` is the shared public surface, `Console.BbcMicro.cs` the platform half, implementing `partial` methods as `[MethodImpl(InternalCall)]` externs). Holds the foundational `System.*` types, `Console` (`System/`) and the runtime helpers `ManagedHeap` (`Runtime/`, namespace `DotNetro.Runtime`). `TypeSystemContext` redirects every framework assembly reference (`System.Runtime`, `System.Console`, `System.Private.CoreLib`, `mscorlib`, …) to it, so the host's framework DLLs are never loaded; other `System.*`/`Microsoft.*` references are an error. `dnrc` and the tests get the build copied to `corelib/<target id>/DotNetro.CoreLib.dll` beside them (a `ProjectReference` with `ReferenceOutputAssembly="false" OutputItemType="Content"` and a `Link`; it must not be a compile reference because its `System.Object` would clash with the real one); `HostAssemblyResolver(targetId)` reads it from there and the playground embeds it as `DotNetro.CoreLib.<target id>`. An `InternalCall` method is routed by name to the function of that name in `src/Irie/Target/MOS6502/runtime.irie` (hand-written MOS6502 MIR: the `__call_indirect_trampoline` and `HeapStart`), so those names must be unique. Calls to fixed ROM addresses are plain C#: `((delegate* unmanaged[BbcMicroOS]<byte, void>)(nint)0xFFE3)(c)` (the `CallConvBbcMicroOS` marker type is in the corelib; `calli` carries it as a return-type modifier and the translator turns it into the `bbcmicro_os` calling convention on the `call.indirect`, see `CallConvention` / `Target.GetCallLowering`; a `call.indirect` of `inttoptr(constant)` lowers to `jsr.abs $addr`). The program's first act is `DotNetro.Runtime.Startup.Initialize` (per target; BBC: MODE 7).

- **DotNetro.WebPlayground** — browser playground: `Microsoft.NET.Sdk.WebAssembly` app exposing `[JSExport]` `Playground.CompileCSharp` (Roslyn) / `CompileForTarget` (`CompilerDriver.Compile(CompileRequest)`) to a Web Worker; `spike/measure.mjs` measures a `dotnet publish` of it under Node. It is built as part of `dotnet test --solution src`. `ClientApp/` is the Vite + TypeScript shell (golden-layout, Monaco); build with `npm run build` after `dotnet publish src/DotNetro.WebPlayground -c Release`

- **DotNetro.Tools.ILSupport** — regenerates `doc/dotnetro/il-support.md` (`dotnet run --project src/DotNetro.Tools.ILSupport`)

- **Irie.Tools.Reference** (`irie-report`) — scores Irie's MOS6502 output against the llvm-mos reference corpus (`ext/llvm-mos-reference/`); see its README and `doc/irie/llvm-mos-comparison.md`

- **Irie** — the compiler backend: unified MIR + MachineCode layers, the pass pipeline and the MOS6502 target (subtargets: BBC Micro, C64). `DotNetro.Compiler` depends on it; it is also usable standalone via the `iriec` / `irie-*` tools. **`src/Irie/AGENTS.md` maps where the layer, dialect, pass-order and target docs live** (loaded when working under `src/Irie`; the 6502 target overview is `src/Irie/Target/MOS6502/README.md`). Pass order, in short: ArithSimplify → IdenticalFunctionFolding (functions with identical bodies fold into one; before inlining so the survivor stays shared) → Inlining (direct calls to single-call-site or tiny generic functions; `func noinline @f` opts out) → RangeNarrowing (value ranges; shrinks arithmetic, compares and loop variables to the bytes they need) → RangeFold (compares the ranges decide become constants) → ArithSimplify again → ConstantBranchFold → UnreachableBlockElimination → ReturnMerge → AbiLowering → Legalizer → InstructionSelector (shape selection) → placement (beam search) → CopyElimination → target post-placement passes → PseudoExpansion.

- **DotLit** — LIT-style test infrastructure; parses `RUN:` and `CHECK:` directives from any comment line; used by both `DotNetro.Compiler.Tests` (`.cs` files, `//` comments) and `Irie.Tests` (`.irie` files for MIR tests, `.s` files for MachineCode tests; all use `;` comments). Also an executable (`dotlit`): `dotlit --regenerate <folder|file>` rewrites the `CHECK` directives to match current RUN output — see "Regenerating `CHECK` blocks" below

### Irie Layer Roadmap

Two layers:
1. **MIR** (`Mir/` + `Dialects/` + `Passes/` + `Target/`) — single IR that flows through every pass, starting in SSA with generic dialect ops on typed vregs and ending as non-SSA target-only ops on physregs
2. **MachineCode** (`MachineCode/`) — low-level machine-code layer (flat instruction stream + labels)

### Test Framework

`DotNetro.Compiler.Tests` runs the `.cs` lit tests in `src/DotNetro.Compiler.Tests/Lit/` (`LitTests.cs`). Each is a small C# program with two `RUN` lines and a `DIFF`: one compiles it with Roslyn and runs it under the host .NET runtime (`dotnet_runner`, in a collectible `AssemblyLoadContext`); the other compiles it with `dnrc` and executes the 6502 binary in the Aemula emulator with BBC Micro OS stubs (`emulator`). `DIFF: dotnet emulated` asserts the two outputs match. Each runs with the default (beam) placement (`LitTest`; see `src/Irie/AGENTS.md`). These are the **only tests that execute generated code**; `Irie.Tests` `.irie`/`.s` lit tests are text goldens. (`DotNetCompilerTests.cs` is legacy and almost entirely commented out.)

#### In-process tools

`LitTestExecutor` splits a `RUN` line into a pipeline (`CommandLine.TryParsePipeline`). When
every stage names a tool with a managed assembly beside it (`<path>.dll`) whose entry-point
class has `public static int Run(string[] args, Stream stdin, Stream stdout)`, the pipeline
runs in-process (`InProcessTool`) with the console bound to in-memory streams (`ToolConsole`),
so JIT and runtime start-up are paid once per test run instead of once per tool launch.
Anything else (`echo`, `cat`, redirects, …) goes through `/bin/sh` as before. The tools do
**not** reference DotLit; a tool is runnable this way when:

- its top-level `Main` just calls `Run` with `Console.OpenStandardInput()` / `OpenStandardOutput()`,
  and `Run` reads and writes its binary stdin/stdout through the streams it is given (text
  through `Console.Out`/`Error`/`In` is routed per run automatically);
- it returns an exit code instead of calling `Environment.Exit`;
- it is safe to run on several threads at once (the lit tests run in parallel), so no
  unsynchronised static state.

A tool that runs another tool (`irie-exec` runs the emulator) finds the in-process runner as
the `"DotLit.RunTool"` `AppContext` value and falls back to launching a process when it is
absent (standalone use). `dotnet_runner` is the one tool that references DotLit, since it has
to bind the console of the program it runs (`ToolConsole.Run`).

`cs_compiler` caches its output per (source, assembly name, `--optimize`), since every lit
test compiles the same file once per `RUN` line. The test projects also set `TieredPGO` off
and Server GC on (`System.GC.Server`), and `Irie` / `DotNetro.Compiler` are built with
`Optimize` on even in Debug (the JIT never optimizes a Debug assembly): each is worth seconds
on the parallel run. Pass `-p:Optimize=false` to step through the compiler in a debugger.

#### Lit `CHECK` blocks: keep them strict (complete listings)

For any `.irie`/`.s`/`.cs` lit test that pins emitted output (e.g. `--emit=asm`),
write the `CHECK` block as the **complete listing** — one `CHECK` line per output
line, in order — not a handful of landmark instructions. Following LLVM FileCheck,
DotLit matches each `CHECK` pattern **literally** (`LitPattern` translates it to a
regex, escaping the literal text); a regular expression is embedded only inside
`{{…}}` holes (e.g. `; CHECK: addr {{[0-9]+}} done`). So a `CHECK` line is just the
**verbatim output line** — no escaping of `.`, `$`, `(`, `)`, etc. — with `{{…}}`
reserved for the genuinely-variable parts. (FileCheck's `[[…]]` variable capture is
not supported.) Matching is an ordered substring search advancing through the run
output (`LitTestExecutor`), and the parser **trims** the pattern
(`LitTestParser` `.Trim()`), so leading indentation is cosmetic. House style:
`; CHECK: ` followed by the verbatim asm line (label at column 0, instructions
indented 4). A loose block (a few landmarks) silently tolerates regressions — extra
or changed instructions between landmarks go uncaught.

To (re)generate a golden, use `dotlit --regenerate` (below) rather than a one-off
standalone `iriec` run — it replays each test's own `RUN` command through the same
tool binaries the harness uses, so the output is the harness form by construction.
This matters for a few static-stack / address-taken frame-slot cases
(`AddressTakenFrameSlot`, `StaticFrameAllocChain`, `FrameSlotStructRoundtrip`),
which emit a *different but valid* allocation form under a hand-rolled standalone
invocation (zero-page-direct `STA $70` vs. an indirect `#<sym`/`#>sym` pointer) —
the regenerator and harness agree, so just regenerate and verify under
`dotnet test`; don't hand-edit a golden to the standalone form.

#### Regenerating `CHECK` blocks: `dotlit --regenerate`

Instead of a throwaway script, refresh the `CHECK` directives in a folder (or a
single file) of lit tests with the `dotlit` tool:

```bash
# Re-run each lit test's RUN commands and rewrite its CHECK directives to match.
dotnet run --project src/DotLit -- --regenerate src/Irie.Tests/Lit
dotnet run --project src/DotLit -- --regenerate src/Irie.Tests/Lit/CodeGen/MOS6502/Foo.irie
```

It resolves the tool variables (`@iriec`, `@dnrc`, `@emulator`, …) exactly as the
test harness does, via `LitConfig.Load`: the nearest `lit.config.json` walking up
from each test file (one per test project root — `src/Irie.Tests/lit.config.json`,
`src/DotNetro.Compiler.Tests/lit.config.json`), whose `substitutions` are paths
relative to that config file with a `${config}` placeholder. It runs against
whichever configuration you invoke it under (`-c Release` for Release; default
Debug), so **build that configuration first**. Each maximal run of consecutive
same-label `CHECK` lines is one **block**; the block is anchored in the RUN output
by matching its existing patterns in order, then replaced by the **complete
listing** of every output line from the first to the last line it matched (the
"envelope" — interior gaps are filled; output before/after the envelope stays
unchecked). This refreshes single-block goldens as they grow/shrink and keeps the
per-function windows of threaded files in place — but it will *expand* a
deliberately-curated partial block to a full listing, so eyeball the diff and
re-run `dotnet test` afterwards. Files with no `CHECK` directives (e.g. the
`RUN`/`DIFF`-only `.cs` tests) are skipped without running their pipelines.

## MOS6502 codegen design reference (llvm-mos)

DotNetro's 6502 codegen is anchored to **llvm-mos** as the reference
implementation. When approaching a compiler **design** question for the MOS6502
target (calling convention, register allocation, frame/stack layout, lowering
choices, peephole opportunities, etc.), check **both** of these — not just one:

1. **llvm-mos output** — compile representative C with the local toolchain and
   read the generated asm / Machine IR:
   - `clang`/`llc` in the local llvm-mos build's `build/bin` (`$LLVM_MOS_BIN`)
   - e.g. `clang --target=mos -Os -S -o - foo.c`; inspect Machine IR with
     `llc -stop-after=…`; use `volatile` to keep stores/loads from being
     optimized away when you want to see the access pattern.
2. **llvm-mos source code** — read the actual pass/algorithm, at
   the local llvm-mos checkout, the parent of that `build/` (target sources under
   `llvm/lib/Target/MOS/`, e.g. `MOSStaticStackAlloc.cpp`,
   `MOSZeroPageAlloc.cpp`, `MOSFrameLowering.cpp`, `MOSRegisterInfo.td`). The
   output shows *what* it does on one example; the source explains *why* and the
   general rule (coloring, benefit model, edge cases) that the output alone can
   hide.

### A pipeline crash is usually a design question in disguise

Errors from the Irie pass pipeline — "no selection rule for `x`", "unexpected
`pseudo.y` survived to the final pass", a legality gap — name a *missing* piece,
not a wrong one. Before touching anything, identify the intended design and fix
the gap at its root:

- **Check llvm-mos first** (per the two sources above). "Should this op be
  `Legal`? how is it lowered? at which layer?" are design questions — answer them
  from the reference *before* writing code, not after a human pushes back. A
  legalizer rule that already exists (e.g. an op marked `Legal`) usually encodes
  deliberate intent; a crash downstream means the *consumer* (selector, expander)
  is missing a case, so add that case rather than rerouting the op to dodge it.
- **Don't accrete workarounds.** If a fix produces a *second* error, or needs a
  special-case branch to suppress an artifact, stop — that is a signal the
  approach is wrong, not that it needs another patch. Back out and reconsider.
- **Don't rationalize.** If you find yourself constructing a confident
  architectural justification for why a hacky-feeling change is actually fine,
  treat that as a red flag and verify the claim (read the pass, run the case)
  before relying on it. State uncertainty plainly instead of inventing a
  constraint to justify the path already taken.
